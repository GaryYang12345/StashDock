# StashDock 功能现状与下一步建议

本记录基于 2026-10-15 的当前代码和本轮界面验收。它是功能盘点与建议，不代表新增功能已经实现，也不替代真实平台和大规模用户验收。

## 已形成的核心流程

- 导入链接、笔记、文件和浏览器书签，编辑标题、正文、标签与封面。
- 网页内容、截图与 favicon 获取；支持用户替换封面。
- 本地应用与 Codex App 共用卡片、导入、编辑、标签和操作样式，并共享本地数据。
- 浏览器扩展在用户现有登录环境中保存当前页面，支持自动跟随页面、编辑信息和待同步保存队列。
- 搜索、分类、标签筛选、收藏、网格/列表、多选和批量发送。
- Windows 独立应用将选中内容导出为 Markdown；文件引用额外附上字节不变的原件副本，通过原生多文件复制或拖拽交给其他应用。
- Codex App 向当前草稿添加带标题的文字上下文。其当前实现不是原始 PDF/Office 文件附件。

定位已经清楚：收集用户认可的资料，整理成可控的参考库，再交给 AI 使用。下一阶段宜完善这条主线的可靠性。

## 优先补齐

### 1. 内容完整度与交付预览

网页查找可提取最多 50,000 字符，浏览器当前页面捕获上限为 20,000 字符。默认 AI 上下文的每条正文也截取到 20,000 字符；手动最终上下文覆盖值有单独处理。

扩展已有“仅捕获可见文字”的提示，但应区分页面折叠、长度截断和内容读取失败，并贯穿收藏详情与导出预览。用户应能确认保存了多少、交给 AI 多少、缺少哪部分。

建议优先统一内容预算与截断标记，提供最终交付预览、字数和原文来源，再考虑分段发送。

代码依据：`extension/page-capture.js`、`src-tauri/src/link_metadata.rs`、`src/lib/context-format.mjs`、`src-tauri/src/library.rs`。

### 2. 原文件交付（按本轮产品决定更新）

当前通用文件导入会保留原始文件字节，文本类文件可读取正文；本地 PDF、DOCX、XLSX 等没有统一的正文解析链路。可导入、可打开和有封面，不等于内容已进入搜索与 AI 上下文。

文件理解由接收端 AI 负责。不要新增本地 PDF、Office、OCR 解析链路。Windows 已实现“原文件 + StashDock 补充说明.md”的原生复制/拖拽，并通过多文件 Shell 与真实剪贴板验收。内嵌面板尚无已验证可用的原生文件草稿接口，保留当前上下文 Add，不能把路径或二进制 MCP 资源当作原生附件。实现及验证详见 `original-file-delivery-20261015.md`。

文件表单目前每个文件上限 5 MB，每批还有数量与总大小限制，后续应按真实目标资料验证是否合适。

代码依据：`src/lib/fileReference.ts`、`src-tauri/src/library.rs` 的 `extract_text`、`plugins/stashdock/server/local-library.mjs` 的 `importFiles`。

### 3. 用户可用的数据恢复与迁移

目前有开发用一致性备份脚本，但界面没有完整的备份、恢复、资料库迁移、回收站与撤销删除流程。

建议先提供包含原文件、封面、正文、标签与元数据的完整导出/恢复，再补删除恢复。复制给 AI 的 Markdown 文件不能替代完整资料库备份。

### 4. 平台真实可用性与管理

平台入口有 X、Instagram、Reddit、LinkedIn、Pinterest、小红书、知乎。本轮已为 Instagram、Reddit、LinkedIn、Pinterest 增加专门的帖子 DOM 适配，七个默认平台均有专门读取路径。新增读取器已通过合成 DOM 和浏览器夹具验证，但尚未完成七个平台的真实登录态验收，不能将代码覆盖等同于生产可用性。

建议公开区分“专门适配”和“通用支持”，按已登录、未登录、长文、展开、弹层、媒体帖等真实页面持续验收。平台整库收藏导入已按用户决定取消，不应重新作为待完成项。

自定义平台目前可新增和打开，缺少重命名、修改地址、删除与整理入口。

代码依据：`src/lib/captureSites.ts`、`extension/page-capture.js`、`src/components/BrowserCapturePanel.tsx`。

### 5. 规模、兼容与交付

桌面资料区仍将当前集合映射为卡片，部分查询和预览流程需要读取整个集合。应在 1,000/10,000 条真实大小正文和缩略图条件下量测启动、搜索、滚动、内存与数据库增长，再决定列表虚拟化和分页接口。

现阶段重点验证的是 Windows 和 Chromium 浏览器侧栏；浏览器书签读取支持 Firefox，不等于 Firefox 的 Save 扩展已经完成兼容。macOS、Safari、不同显示器/DPI、签名安装和升级回滚还应有独立验收。

商业发布前还需首次启动引导、扩展连接状态、保存/同步状态、数据位置和恢复入口，以及用户可主动导出的诊断信息。

### 6. 小的界面一致性余项

卡片、页脚与 `ReferenceFileImport` 的选中文件标题区已共用彩色 `ReferenceGlyph`。平台提示框远离名称的问题也已修复。

## 建议开发顺序

1. 内容完整性、截断说明、最终 AI 交付预览。
2. 原文件交付与补充说明，文件理解交给接收端 AI。
3. 完整资料库备份/恢复与删除恢复。
4. 重点平台的真实登录态验收与自定义平台管理。
5. 大资料库性能、首次使用和分发升级体验。

当前适合围绕核心流程开展小范围真实用户试用。商业版本的主要缺口是内容可信度、数据可恢复性和目标环境的长期验收，而非继续堆叠平台数量。
