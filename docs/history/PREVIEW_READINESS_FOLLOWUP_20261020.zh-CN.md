# 默认封面增多与 Content 更新行为复核

## 现场证据

- 用户本轮重新导入后实际库为 66 条；第一次只读检查为 13 条有图、39 条有正文。图片任务 20 条首轮 failed、1 条 working，其余还未尝试；不能把 job failed 数直接当作无封面数，因为已经成功截图、尚缺图标的任务也会标记 failed。
- 再次只读检查：28 条 failed 中 16 条无封面。`web_preview_runtime_version` 仍为 `system-webview2:capture-v1`，ChatGPT 缓存 Node PID 11680 从 15:51 持续运行。旧进程仍使用其内存中的旧 worker；上次文件同步未等于实际队列接管。
- v4 就绪门槛还存在另一独立风险：慢字体、可见图片、持续 aria-busy 或动态文本能阻止 ready/stable，10 秒后丢弃已有画面。不能证明现场每条失败均由它导致；例如隔离的同一 GitHub URL 在旧策略实测也可成功。

## 有界修正

v5 将“页面已有可绘制内容”和“最佳截图时机”分开。正常仍等待图片、字体和布局稳定；5 秒后有内容的页面允许 best-effort 截图，不因未结束的子资源直接回退默认。真正空视窗仍失败，不突破原有总超时、并发、公共网络安全边界。

这不是“所有页面完整加载”的保证。复核 Uiverse 输出仍曾出现顶部正常、元素区空白；网络/子资源失败和网站异步加载仍需进一步验证，不能仅凭返回了 JPEG 声称质量问题已全部解决。

## Content 的当前实际语义

- 浏览器书签导入 / 粘贴链接立即保存，后台独立补原始正文与临时标题，失败有限重试。首次取得非空正文后不持续抓取网页；公开 HTTP 读取不保证登录或动态正文完整。
- Desktop 的 ContentEditor 只在切换 item ID 时初始化编辑文本；它持有打开时的内容，不订阅后续原始正文变化。MCP 打开时也先取一次 context，编辑期间暂停列表轮询。因此已经打开的 Content 不会实时更新；关闭重开会读取当前数据。
- 打开编辑器本身不写入 override、不停止后台。点击 Save changes 会写入用户最终 context override，后台按设计不覆盖该引用的内容；即使保存的文本与打开时相同，也遵循这一规则。
- 本次不擅自改变编辑器的实时更新/草稿保留行为。若后续调整，应只更新未编辑的草稿，禁止覆盖用户已经输入的内容，并在两个宿主共用同一逻辑。
