## 已确认的瓶颈

1. Desktop 和 MCP 通过共享数据库租约选出一个后台所有者，但该所有者一次只执行一项任务。慢页面会阻塞后续页面。
2. 每次截图调用 `with_browser`，新建临时 profile、公开网络代理、STA 线程和 WebView2 会话，随后关闭并清理。MCP 还为每个任务启动一次原生 helper。不是复用一个批量渲染引擎。
3. 渲染总预算 22 秒；收到有效主文档后，等待 load + 1 秒或收到主文档后 5 秒才发截图请求。截图失败或缺少内联 favicon 时，还可能串行执行 8 秒元数据请求及最多 4 秒图片/favicon 请求。清理也占用当前任务生命周期。Desktop 能通过中间回调提前发布图片，但 MCP helper 目前一次性输出 JSON，并在进程结束、临时目录清理后才 resolve，因此 MCP 可能把已完成的截图继续等在后续图标工作后面。
4. MCP 在 2 秒 tick 上领取后续任务，任务结束到下一次 tick 之间还有最多约 2 秒间隙。
5. 排序只区分“缺封面”和“只缺 favicon”，之后按收藏时间倒序；不知道当前视窗可见哪些卡片，也没有把未尝试任务优先于到期重试。
6. 失败冷却 600 秒，最多尝试 3 次。这意味着失败后的默认封面可能维持至少 10 分钟。不能通过持续 skeleton 假装这段时间仍在截图。
7. 截图缓存目前仅为进程内 8 项、180 秒的 single-flight 缓存；SQLite 中持久保留的是收藏的 preview 和 favicon 缓存，没有独立的跨删除重导入截图缓存。删除收藏再导入同一 URL，通常需要重新截图。

## 推荐路线（已批准，分步验证）

### 第一阶段：解决吞吐和首屏体验

- 保留当前系统 Evergreen WebView2，不捆绑 Chromium，不使用用户浏览器登录态，不增加云截图服务。
- 按需启动同一套原生截图 worker；批量任务期间复用专用 WebView2 environment，空闲后释放。Desktop 和 MCP 复用同一实现，以现有租约协调所有权，不再增加第二套数据库或常驻服务。
- 在专用 environment 中评估两个隔离页面槽，从小并发开始。重用页面时必须隔离站点状态，重置任务代次、网络事件和超时，保留公开网络代理、权限/下载/弹窗拒绝以及原有资源边界。不要复用桌面 UI 的 WebView。
- 统一控制前台截图、后台补图及 PDF 渲染的总额度，而不只是每个进程各有限额。后台单所有者并不等于所有前台 helper 也共享同一额度。
- 可见缺图卡片优先，然后下一屏，再处理其他首次任务，最后执行到期重试。滚动只调整待执行队列，不反复取消正在正常完成的任务，也不能让后台任务永久饥饿。
- 页面达到可截图状态后尽早输出，而不是只依赖 load 或固定等待；仍需验证截图不是空白、错误页、登录页或挑战页。对慢任务使用受限预算和有界重试，避免一个网站反复占住队头。
- 封面完成立即发布；favicon 和其他非必要工作不能阻塞下一张封面的执行。保留自定义封面优先和 ID + URL 的过期结果校验。
- 在内部保留有界的阶段耗时、失败类别用于验收，不增加用户设置、诊断状态或大量提示。

### 第二阶段：评估重复导入的缓存收益

- 先量化冷导入和热导入差异，再决定是否增加有容量/有效期上限的派生图片缓存。
- 缓存必须按规范化 URL、截图参数及渲染策略版本区分，不能复用不同授权范围的截图。
- 不无限保留派生图片，不在缓存和收藏里重复存储相同的大图，不改变原文件和用户元数据的语义。

### 不建议

- 直接把并发开到 8–16，仍为每页反复启动完整浏览器。
- 靠无限 loading 动画、缩短超时或降低图片质量掩盖失败。
- 默默改成只取 OG 图，并把它当成真实网页截图。
- 把收藏 URL 发给第三方云截图服务作为默认路径。它会引入外传、费用和外部依赖，不在本次范围。

## 默认 Web page 封面现状

`PreviewArtwork` 的实际顺序为：

1. 没有 preview 且状态为 queued/working：显示 loading skeleton。
2. 有 preview 且图片解码成功：显示截图、分享图或用户封面。
3. 没有 preview，或图片解码失败：显示按类型定制的默认封面。

没有图片可能来自访问/网络失败、登录或反爬、渲染/资源预算失败、网页不提供可用分享图，或没有活跃截图 worker。失败/等待重试、worker 尚未启动和图片加载失败在当前 UI 都会走默认封面，不能仅根据外观确定根因。默认封面不代表链接保存失败，也不是正文抓取是否成功的证明。

## 验收标准

- 比较同一批公开 URL 的旧/新冷导入、热导入；不拿不同站点或不同网络的结果相减作为提速证据。
- 分开记录首张、首屏、整批完成时间和成功率；包括失败网站及重试，不只测易加载页面。
- 测量所有自有 helper/WebView 子进程的 CPU、峰值内存和空闲释放，不只看主程序。
- 验证滚动优先级、混合慢快页面、取消、崩溃恢复、重复启动、删除后迟到结果、跨宿主租约交接和自定义封面保护。
- 本文未承诺固定倍数或“65 条几秒全部完成”。实际收益必须由本机对照实验确认。

## 本轮实现与验证

新增独立正文队列，批量收藏与单条 URL 共用 `fetch_content`；只填空白且未编辑最终上下文的浏览器收藏，同时事务更新全文索引。图片队列仍只处理图片，不把正文请求塞回截图串行队列。已有收藏也可补全，无须重导入。

截图复用专用 WebView2，会话任务间暂停脚本、清理站点数据、取消旧连接并重置事件域；空闲 20 秒释放，最多存活 180 秒。MCP 通过有界 NDJSON 会话连续提交任务，图像回调立即写回，不再等 helper 退出/清理后才显示。取消和超时仅结束自有 helper。Windows 两个跨进程渲染名额覆盖前台、后台和 PDF；后台仍保持单截图任务，不通过放大并发换速度。未尝试任务优先于重试，重试冷却从十分钟调整为两分钟，最多三次。

本机三条公开 URL 的小样本：新版真实截图耗时 3964 / 5334 / 5629 ms，旧版逐任务冷启动为 6691 / 9767 / 8613 ms；同一组站点/图片尺寸/图标输入，非交替运行，网络与执行顺序仍是干扰项。三次新任务只创建一次浏览器并复用两次；Rust Learn 页两条正文路径均为 1883 字符且逐字一致。这是机制验证，不是整批 65 网站、成功率或整机 CPU/内存节省承诺。对应记录：`output/link-enrichment-renderer-smoke.log`。

尚未实施：按 UI 可见卡片/下一屏调整队列、基于页面稳定程度缩短截图等待、非必要图标维护彻底移出截图串行队列、删除重导入 URL 的跨生命周期持久图片缓存。当前优先交付正文一致性与已验证的复用机制，不把这些后续收益算作已完成。
