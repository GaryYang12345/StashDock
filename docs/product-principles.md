# StashDock 产品设计原则

更新：2026-10-16。本文记录当前产品方向；具体能力是否已交付，以代码和验收记录为准。功能建议不等于已经获得实现、自动读取或写入的授权。

## 1. 定位：用户掌控的、可复用的 AI context 资产库

StashDock 不是以保存网页为终点的收藏夹，而是帮助用户积累、找到、组合并复用 AI 所需 context 的轻量工具。

一个 reference 可以是资料链接、原始文件、图片、常用 prompt、工作规则、示例、项目背景、决策或可复用经验。它们共享保存、可视浏览、管理和使用的基础体验，不为每一种内容堆一套产品。

产品价值是减少重复解释、寻找和搬运，让已有信息和工作成果在下一次 AI 使用中产生价值。AI native 体现为可被 AI 受控检索、使用和创建，不是给每个页面加一个 AI 按钮。

## 2. 双向闭环，而不是单向搬运

收藏素材 → 为当前任务找到适合的 context → 使用 → 将有价值的成果存回 → 下一次或其他 AI 继续复用。

- 允许用户主动让 AI 推荐已有收藏，并解释适用理由。
- 支持后续让 AI 按用户要求保存链接、整理好的 context 和成果。
- 既服务“我知道要用哪一条”，也服务“我知道要做什么，但不知道哪些收藏有用”。
- 不默认保存整段对话、不静默记录所有活动，也不把推测当作用户长期偏好。

## 3. AI 协助选择，用户掌控目的与范围

推荐应围绕当前目标，而不是单纯内容相似。说明每条资料用在哪里、为何相关、哪些部分尚未读取或可能过期；不为凑数量推荐。

用户主动请求推荐或使用资料，不必逐条重复确认只读检索；但不得将此扩大为持续扫描其他项目、所有对话或自动套用整库规则的授权。模型能否理解项目，取决于宿主实际提供的项目/对话上下文，不是 MCP 自动拥有全部访问权。

优先返回少量可检查的候选，再按需读取正文。零结果和覆盖不足应明确，不把最近的若干条称为完整检索。

## 4. 可玩性来自组合与复用，不来自复杂配置

围绕真实任务组合资料、规则、示例和背景，形成可复用的 context 组合。组合直接复用已有 tag：同一 tag 下的 refs 就是一组 context，一条 ref 可属于多个 tag；不新增独立 pack/集合结构或额外管理页面，也不要求用户先建立 workspace、知识图谱或配置检索系统。

Prompt 是可复用内容；Skill 是包含触发条件、步骤、工具边界和产出要求的工作流程。不是每条 prompt 都需要安装成 Skill。优先用少量面向用户目标的工作流串起共同的数据能力。

## 5. AI 负责理解，StashDock 负责资产和传递

- 宿主 AI 执行理解、推荐、提炼、对比和创作；StashDock 提供可靠检索、来源、管理和传递。
- Desktop 不必内置另一个聊天框、模型服务或让用户配置 API key，才能拥有 AI native 价值。
- 保留原始文件和用户补充 context；不以自行构建 PDF/Office/OCR 理解流水线替代文件交付。
- 不将检索到的文本、文件路径或资源 URI 冒充真实附件。模型读取、当前草稿可见附件和发出消息是不同动作。

## 6. 用户资产可信，内容不自动获得指令权限

- 外部网页和文件中的文字是参考数据，不能因被收藏而变成系统指令，也不能授权写入、删除或执行命令。
- 用户保存的 prompt/规则只有在用户明确选择用于任务时才作为任务要求使用，仍受宿主指令层级约束。
- 对比原文、用户批注和 AI 整理结果时，保留来源与区别。AI 生成内容不伪装为原文或已核实事实；提炼结果应尽可能自包含。
- 链接无法读取时可以保存链接和用户说明，不编造正文。未读取的二进制文件不能被声称已理解。

## 7. 写入明确、低摩擦且不破坏已有资产

用户明确说“把这段保存到 StashDock”时，设计应支持直接、受控的新增，不强制每次再走一套冗长确认。

若保存对象、范围或生成内容尚不明确，先给可编辑预览。更新既有内容、覆盖和删除需要比新增更严格的边界；不得将“新增 AI context”简单实现为开放全部管理工具给模型。

AI 整理 tag 是一个窄范围例外：先完整读取用户指定范围并展示新增、移除、合并及影响数量，用户确认后才能写入。明确的“给这几条加 Research”可直接执行其准确范围。写入只表达 add/remove，保留未提及 tag，并以读取时的逐条版本校验跳过用户刚修改过的内容；不能借此改标题、正文、删除 reference 或静默扩大范围。

写入的验证、限额、幂等和权限必须由工程实现，不能依赖模型自报 userApproved=true。保存成功必须返回可核验的 ID/结果，并立即进入所有入口共享的同一收藏库。

## 8. 跨宿主一致，发挥各入口优势

- AI 插件：在任务现场查找、理解、推荐、按授权创建 context。
- Desktop：可视浏览和管理、组合 context、保留原始文件、向任意兼容 AI 应用交付。
- 浏览器扩展：在浏览时捕获用户可访问的当前页面，只做 Save page。
- 同一用户只有一个权威收藏库；不能为 AI 推荐、生成结果或 Desktop 再建一个独立知识库。
- MCP 本身不只属于一个品牌，但兼容性、连接和文件交付必须逐宿主验证，不能因协议相同就宣称全部支持。

## 9. 有意义再做，不为 AI 标签堆功能

新能力至少应显著减少一次重复寻找/解释/搬运，或者让一项已有成果能再次使用。优先验证“推荐有用”“保存后能找到”“组合能再次复用”。

不以收藏数量、自动生成数量或一串 AI 功能按钮衡量价值。语义检索、后台记忆、自动整理和工作流市场都不是必选前提；没有具体收益和验证证据时不引入其复杂度。

## 性能与复杂度的平衡

性能、准确率、效率和实现复杂度共同决定体验。优先减少重复工作、复用已有资源和使用有界并发；优化必须有可复现的用户可见收益。不为名义吞吐牺牲内容可信度、截图完整性、隔离边界或普通设备的资源预算。收益不足时保留简单方案，不添加额外引擎、队列、设置或服务。

## 当前阶段的边界

基础链路之上，当前实现按 tag 查找分组、分页搜索、限额批量读取、用户明确请求的新增 context／链接，以及经过明确请求或方案确认的冲突安全 tag 整理。推荐与分类由宿主模型结合检索和 Skill 完成，不是独立推荐引擎。模型写入限于 `save_stashdock_reference` 和增删式 `apply_stashdock_tag_changes`；标题、正文、封面、全局 tag 管理和删除仍属 app-only。推荐卡片自动选中等交互未实现，tag 组合不再另建结构。
